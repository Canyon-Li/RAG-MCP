# 企业研报知识服务产品 · 技术落地方案

> 定位：企业内部（券商研究所 / 银行理财子 / 财富管理机构）研报知识服务产品，**纯 Web 服务形态**（不做 MCP）。
> 本文是目标态设计 + 从现有 RAG-MCP 仓库演进的迁移路径。日期：2026-08。

---

## 1. 产品形态与角色

| 角色 | 用途 | 界面 |
|---|---|---|
| 业务人员（客户经理/投顾/销售） | 晨会速览、客户问题即答（评级/目标价/盈利预测）、观点溯源到页码（合规要求） | 聊天问答页：引用可点开、按股票/行业/时间过滤、"只要最新版"开关 |
| 知识库管理员 | 每日增量入库、公有库审核、重复/过期报告巡检、检索质量评估 | 管理台（入库/trace/评估/数据浏览） |
| 分析师（内容供给方） | 产出研报入库 | 上传入口 + API |

**库模型**：每人可见 = 1 个公有库（全公司共享、管理员维护）+ 1 个个人库（自己上传、自己可见）。后续可扩展团队库（部门级），数据模型预留 `owner_type`。

**规模假设（设计目标，不是虚报运营数字）**：公有库存量 1–10 万篇研报、日增百篇级；个人库每人 ≤ 数百篇（配额限制）；并发问答峰值 ~10 QPS。

## 2. 总体架构

```
浏览器（聊天页 / 管理台）
   │ HTTPS
Nginx
   │
FastAPI 应用层
   ├─ /api/query        问答（会话、权限、流式 SSE）
   ├─ /api/ingest       上传（异步任务、进度查询）
   ├─ /api/library      库/文档管理（列表、删除、配额）
   └─ /api/admin        评估、trace、巡检
   │
   ├────────────────────────────┬──────────────────────────┐
   │ 检索服务                     │ 摄取 Worker（异步队列）    │
   │ 查询理解 → 双路召回 → RRF    │ 解析(Docling) → 指纹      │
   │ → 跨库/版本去重 → 重排       │ → 切块 → embed(缓存)      │
   │ → 生成(带引用)               │ → upsert → 状态回写       │
   └────────────────────────────┴──────────────────────────┘
   │              │                 │              │
向量库          词法索引          元数据库        模型服务层
Milvus/Chroma   BM25(小)→ES(大)   PostgreSQL     vLLM / TEI
```

**MVP 态（现仓库可支撑）→ 企业态演进**：

| 组件 | MVP（可立即落地） | 企业态（规模/合规驱动） |
|---|---|---|
| 向量库 | Chroma + metadata filter（library_id） | Milvus standalone，`partition_key=library_id`（官方多租户模式） |
| 词法索引 | 内存 BM25（现有 JSON 索引，按库分文件） | Elasticsearch/OpenSearch（10 万篇级后内存 BM25 不可持续） |
| 元数据 | SQLite | PostgreSQL（用户/权限/任务/审计） |
| 应用层 | FastAPI + Streamlit 聊天页 | FastAPI + React 前端（SSO 对接内网统一认证） |
| 摄取 | 后台 worker 进程 + DB 状态表 | Celery + Redis（重试/优先级/死信） |
| 模型服务 | Ollama（本地单机） | vLLM（生成/Embedding）+ TEI，GPU 池 |

## 3. 模型选型（2026-08 时点，全部真实可落地）

### 3.0 外包交付形态：谁选模型、谁出算力

交付场景：**乙方（外包）为券商开发本系统**。行业既成事实——2025 年初已有至少 16 家券商完成 DeepSeek-R1 本地化（国泰君安/国金/中泰/兴业等），2026-05 起多家迭代部署新版；恒生"智营"、顶点 LLM 投顾平台均为供应商交付案例。券商的模型平台是持续迭代的基础设施，**不是本项目的采购项**。

| 主体 | 职责 |
|---|---|
| 甲方·信息技术中心 | GPU 算力、私有化模型平台（DeepSeek/Qwen 系）、对内 OpenAI 兼容 API、模型升级 |
| 乙方（本项目） | 应用层全链路：RAG 管线、检索、版本管理、多库、前端、评估运维——**不选型不采购模型** |
| 甲方·业务部门（研究所） | 研报语料授权、评测验收 |

乙方的两项模型工作：

1. **模型无关适配层**：所有模型调用走 OpenAI 兼容协议 + 配置切换（仓库 Factory+Registry 模式即此形状），交付时适配甲方平台型号，平台模型升级应用零改动。
2. **向信息技术中心提《模型能力需求清单》**：生成模型需支持 JSON mode / 指令遵从 / 上下文 ≥32K；是否提供 Embedding 与 Vision 服务——**甲方平台通常只有 chat 模型，Embedding/Reranker/VL 由乙方作为应用组件部署在甲方内网**（小模型、单卡或 CPU，数据不出域合规）。

下文 §3.1–§3.4 的具体型号 = 乙方自托管组件的选型 + 交付演示环境的默认配置；生产环境的生成模型以甲方平台为准（通常为 DeepSeek-R1/V4 系或 Qwen 系 32B–671B），应用层无改动切换。

### 3.1 部署形态决策（合规优先）

| 机构类型 | 形态 | 理由 |
|---|---|---|
| 券商研究所/总部 | **全私有化**（开源权重 + vLLM，可选昇腾信创栈） | 研报为内部资料，数据不出域是硬约束；21 家银行矩阵化部署 DeepSeek/Qwen 已是行业事实 |
| 银行理财子 | 全私有化（信创：昇腾 910B + vLLM-ascend / MindIE） | 同上 + 信创要求 |
| 财富管理/三方小机构 | **混合**：检索组件（Embedding/Reranker）自托管，生成可走 DeepSeek-V3.2 API | 向量本质是文本的变换，视为敏感数据不出域；生成侧 API 成本极低（输入缓存命中约 $0.028/百万 token） |

### 3.2 LLM 按角色选型（一个产品里 LLM 不是"选一个"，是按角色分工）

| # | 角色 | 私有化推荐 | 低配/替代 | 选型理由 |
|---|---|---|---|---|
| 1 | **答案生成**（面向业务人员，带引用） | Qwen3-32B（AWQ/FP8） | Qwen3-14B；API 档 DeepSeek-V3.2 | 中文金融语料强；指令遵从（引用标注、冲突并列、拒答）在小尺寸上明显掉档，生成不要省 |
| 2 | **查询理解/改写**（实体识别、时间词、指代消解） | Qwen3-8B | Qwen3-4B | 结构化输出（JSON mode）稳定即可，高并发下延迟敏感，用小模型 |
| 3 | **元数据兜底抽取**（业务指纹低置信时） | Qwen3-8B | 规则优先，LLM 只兜底 | 输出是结构化字段（券商/分析师/代码/日期），校验由正则回查 |
| 4 | **评估 Judge**（离线评测） | 与生成器**异族**：DeepSeek-V3.2 API 评 Qwen 生成（或互换） | — | 避免同族模型自偏好（self-preference）导致评估虚高——方法论上必须异族 |
| 5 | **图表/版面 Vision**（K线/柱状图→文本） | Qwen3-VL-8B（AWQ） | Qwen3-VL-2B（单卡 24G 内） | 开源 VLM 图表/文档理解第一梯队，替代现 llava-phi3（后者图表数字识别差） |

**不选的**：通用 Agent 型多模态大模型一把梭（贵、慢、引用不可控）；生成用 0.6B–4B 小模型（引用遵从不达标，金融场景直接出合规问题）。

### 3.3 Embedding / Reranker

| 模型 | 维度/上下文 | 评价 | 结论 |
|---|---|---|---|
| **Qwen3-Embedding-4B** | 可变（Matryoshka 32–1024） / 32K | 2025-06 发布，8B 版 MTEB 多语言第一；instruction-aware | **首选**，维度取 1024 |
| Qwen3-Embedding-0.6B | 同上 | 质量仍超上一代中文模型，CPU 可跑 | 低配/开发档 |
| BGE-M3 | 1024 / 8K | dense+sparse+colbert 三模、TEI 一键部署、中文企业存量最大 | 稳妥备选（生态最成熟） |
| bge-large-zh-v1.5 | 1024 / 512 | 上一代 | 新项目不推荐 |
| nomic-embed-text（现仓库在用） | 768 | **英文为主**，中文研报召回吃亏 | **P0 必换**——这是当前仓库最大的质量短板之一 |

- Reranker：**Qwen3-Reranker-4B**（与 Embedding 同族配套）；轻量备选 bge-reranker-v2-m3（2GB 级，CPU 可跑）。
- **词法侧保留 BM25 + 金融自定义词表**，不用 learned sparse 替代：股票代码（`300442` vs `300443`）、财务术语（"扣非归母净利润"）这类**精确匹配**，稠密向量区分度差，BM25 是刚需；词表 = 股票简称/代码别名表（"宁王"→宁德时代）+ 行业黑话，jieba 自定义词典已支持。

### 3.4 推理服务与 GPU 配置（真实规格）

| 档位 | 硬件 | 跑什么 | 说明 |
|---|---|---|---|
| 开发验证档 | 1–2× RTX 4090 24G | Qwen3-8B-AWQ（生成）+ Qwen3-Embedding-0.6B + Qwen3-VL-2B/4B | 单机自测、简历项目实际可跑 |
| 企业起步档 | 2× A800-80G | 卡1：Qwen3-32B-AWQ；卡2：Qwen3-VL-8B + Embedding-4B + Reranker-4B（vLLM/TEI 分时） | 数十人团队够用 |
| 企业标准档 | 4–8× A800/H800 或昇腾 910B | 32B 高并发 + 独立 Embedding/VL 服务 + 预留微调（LoRA 对齐研报文风/术语） | 矩阵化部署（多模型多场景）是银行/券商已验证路线 |

粗算并发：50 名业务人员峰值 ~10 QPS 生成请求，32B-AWQ 单卡批处理吞吐完全覆盖；瓶颈更可能在摄取（日增百篇 × Vision 描述），所以摄取走异步 worker 与在线推理分池。

### 3.5 成本量级（API 档粗算）

单次问答上下文 ≈ 8K tokens（10 chunk × ~800 token）。按 DeepSeek-V3.2 官方价（输入缓存命中 ~$0.028/百万、标准输入 ~错峰更低），**万次问答的生成成本在个位数美元量级**——生成 API 化的成本可忽略，真正的成本是 GPU 摄取（图表描述）与运维。这解释了为什么本方案把工程重心放在**摄取增量化和检索质量**而不是模型上。

### 3.6 规模够用性评估（外包验收视角）

"够用"的裁判是验收指标（source_recall / 引用准确率 / 人工抽检），不是参数量。分角色结论：

| 角色 | 结论 | 边界与对策 |
|---|---|---|
| 生成 32B 级 | **够用**——RAG 生成是"依据给定证据提取、组织、引用"，难点在检索质量不在参数量；2025 年券商落地的问答/助手类应用普遍 32B 级 | 复杂多跳数值任务（对比多家盈利预测并计算）会算错：①甲方平台有大模型（满血 671B/V4）按意图升路；②**数值计算外置**——表格经 TableFormer 结构化后代码计算，不让 LLM 心算；③引用约束+低置信拒答 |
| 查询理解 8B | 够 | 实体识别/改写/JSON 输出是舒适区 |
| Embedding 0.6B–4B | 够 | 检索任务不需要大模型；瓶颈在分块与金融词表 |
| Reranker 0.6B–4B | 够 | — |
| Vision 8B | 基本够 | K线/柱状图描述够；复杂多级表格截图不硬看图——走解析层结构化通道，Vision 兜底图表类 |

并发账：券商全员数千但研报问答日活预估百级、峰值 QPS 个位到几十，32B-AWQ 两卡批处理可扛；属甲方平台层容量问题，乙方在需求清单中写明压测指标即可。

## 4. 公有库 + 个人库：数据模型与隔离


### 4.1 元数据模型（PostgreSQL；MVP 态 SQLite 同构）

```sql
users(id, name, dept, role)                          -- role: biz/admin
libraries(id, owner_type, owner_id, name, quota)     -- owner_type: public/personal/team
documents(id, library_id, business_key, file_hash,   -- business_key: 业务指纹(§7)
          title, broker, analysts, stock_codes, industry,
          report_date, report_type, status,          -- status: pending/active/superseded
          uploader_id, created_at)
chunks(vector_id, doc_id, library_id,                -- library_id 冗余进 chunk，检索过滤零 join
       content_hash, page, section, text)
ingest_tasks(id, doc_id, state, progress, error)     -- 上传进度回写
audit_log(id, user_id, query, sources, ts)           -- 谁问了什么、引用了什么（金融审计）
```

### 4.2 存储隔离与权限规则

- **向量库**：单 collection（统一 schema），`library_id` 为过滤字段；企业态用 Milvus `partition_key=library_id`（公有库数据量与个人库物理隔离、同一条查询仍可跨 partition）。
- **权限只在服务端解析**：`可见库集合 = [public] + [personal(uid)]`，检索 filter 由服务端注入 `library_id ∈ 可见集`；客户端传来的任何库过滤条件必须与该集合求交集。**不做检索后过滤**（先召回再按人筛会导致个人库内容泄漏到召回池）。
- 个人库 chunk 对其他任何用户不可见；审计日志记录每次问答的来源库。
- 员工转岗/离职：库属主关系在 `libraries` 表，权限收敛即收敛，向量数据无需迁移。

## 5. 检索全链路（九步，含边界处理）

```
用户问题 ─→ ①权限解析 → ②查询理解 → ③双路召回 → ④RRF融合
         → ⑤跨库/跨版本去重 → ⑥重排 → ⑦上下文组装 → ⑧带引用生成 → ⑨低置信兜底
```

1. **权限解析**：uid → 可见库集合（§4.2），注入检索 filter。
2. **查询理解**（规则 + Qwen3-8B 混合）：
   - 实体识别：股票代码/简称（别名表归一化"宁王"→300750）、行业、券商名；
   - 时间词解析："最新"→ recency 加权 + `report_date` 过滤/排序；"去年三季度"→ 区间过滤；
   - 指代消解（多轮）："那它的目标价呢" → 用会话历史改写为完整查询；
   - 输出 `QueryPlan{rewritten, entities, filters, recency, intent}`，全部落 trace。
3. **双路召回**（每路 top-50，同 filter：`library_id ∈ 可见集` + 股票/行业/日期/类型）：
   - Dense：Qwen3-Embedding（1024 维）；
   - Sparse：BM25 + 金融词表（代码与术语的精确命中）。
   - **一次查询跨库召回**（filter IN），不做分库两次查询再拼——避免库间分数不可比；库级偏好交给第 ⑥ 步重排与可配置权重。
4. **RRF 融合**（k=60），结果带 `library_id` 来源标记。
5. **跨库/跨版本去重**（版本管理的检索侧落点）：
   - 同 `content_hash`（同一报告既在公有库又在个人库）→ 保留公有库权威副本，去重后不足 top-k 回补召回池；
   - `status=superseded` 的文档默认剔除（"只要最新版"开关闭合时；用户明确问历史时放行）；
   - 同业务键不同日期（周报系列）不合并——它们是不同文档。
6. **重排**：Qwen3-Reranker-4B，50→10；分数低于阈值 τ 的直接丢弃。
7. **上下文组装**：同文档相邻 chunk 合并为逻辑段（避免碎片引用）；每段注入 `[报告标题 | 券商 | 日期 | 页码]` 引用标记；总量 ≤ 12K 字符。
8. **带引用生成**（Qwen3-32B，低温度）——prompt 硬约束：
   - 只依据上下文作答，每个观点标注引用编号；
   - **观点冲突并列呈现**："中信（2026-06）看多目标价 46 元；华泰（2026-07）中性，认为估值已反映产能投放"——金融问答的核心价值之一就是呈现分歧而不是编一个答案；
   - 数据必须带"截至日期"（目标价/盈利预测是时点数据）；
   - 固定页脚："内容摘自券商研究报告，仅供内部参考，不构成投资建议。"
9. **低置信兜底**：重排后无 chunk 过阈值 → 固定话术拒答 + 建议改问法（如提示按股票代码查询），**不硬答**——金融场景编造一个目标价是合规事故。拒答同样落 trace 进评估集。

## 6. 边界情况清单

| 情况 | 处理 |
|---|---|
| 个人库为空 / 刚注册 | 正常走公有库；不提示"无权限"类报错 |
| 同一报告在公有库与个人库都有 | 检索去重保公有库副本；上传时就地提示"公司库已有此报告"（按业务指纹查重） |
| 时间敏感问题（"最新目标价"） | recency 加权 + 默认剔除 superseded + 答案带报告日期 |
| 多空观点冲突 | 并列呈现 + 各自出处（§5.8） |
| 上传中（未入库完成）的文档 | `status=pending` 不进检索索引，页面显示解析进度 |
| 超配额/超大文件 | 拒收并提示；>100 页研报转异步并预估耗时 |
| 员工权限变化 | 服务端每次查询动态解析可见库集合，无缓存泄漏 |
| 问题里含股票代码 | 代码走 BM25 精确命中 + `stock_codes` 元数据过滤双保险 |
| 用户问"我的笔记里怎么记的" | 意图识别为个人库优先，检索权重偏向 `personal` 库 |

## 7. 入库链路（异步，含审核与查重）

```
上传(PDF) → 类型/大小校验 → 业务指纹(首页要素正则: 执业编号/证券代码/日期/券商)
  → 查重: 命中公有库同指纹 → 提示"公司库已有"（可仍存个人库，检索去重兜底）
  → 入队(异步worker) → Docling解析(DocLayNet版面+TableFormer表格) → 章节对齐切块
  → Transform(Qwen3-VL图表描述[持久缓存] + 规则式元数据富化)
  → Embedding(内容哈希缓存: chunk未变直接复用向量)
  → upsert(向量库+BM25) + 旧版本chunk清理(同业务键superseded级联删)
  → 状态回写 → 页面进度
```

- 公有库入库需管理员**审核**后 `active`（研报入库合规动作）；个人库自动 `active`。
- 增量化（对简历的核心卖点）：文件 SHA256 短路 → chunk 内容哈希比对 → 未变 chunk 跳过 embed；图表描述按图片哈希持久缓存。41 页研报全量 ~24–55 min（现仓库 trace 实测）的目标增量耗时待实测（parse 全量 ~4 min 是底价，省的是 transform 70%+ 与 embed）。
- 已知坑（面试讲）：chunk 边界漂移——前置章节增删导致后续 chunk 哈希全变、增量失效；按研报章节结构对齐切块缓解。

## 8. 合规与审计

1. **数据不出域**：私有化部署或仅生成侧走 API（机构合规部门确认前提下）；Embedding 永远自托管。
2. **引用可溯**：答案逐观点标注 [报告 | 页码]，业务人员转发客户前可人工核对——这是产品对"AI 编造"的合规防御。
3. **AI 生成标识 + 免责声明**：遵循《生成式人工智能服务管理暂行办法》标识要求；产品定位**信息检索辅助**，不做投资建议生成（不碰投顾牌照边界）。
4. **审计**：`audit_log` 记录 uid/query/引用来源/耗时，金融检查可导出。
5. **版权**：研报内部使用授权范围确认；语料不对外分发。
